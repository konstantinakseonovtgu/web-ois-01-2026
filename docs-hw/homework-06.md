# Задание к практике 6

## Часть 1. Закрыть прямую ссылку на неопубликованное (3 балла)

На практике нашли дыру: `/events/4` открывает «Сталкер», который ещё на модерации. Причина —
в API: `GET /api/events/{id}` отдаёт мероприятие в любом статусе.

Правило (BR-9): неопубликованное мероприятие видят только организаторы его клуба и
администратор. Остальным — **404**, как будто мероприятия нет.

| Кто | `GET /api/events/4` (на модерации, Киноклуб) |
|---|---|
| без входа | 404 |
| Анна (студент) | 404 |
| Глеб (организатор шахматного клуба) | 404 |
| Ирина (организатор Киноклуба) | 200 |
| администратор | 200 |
| кто угодно, `GET /api/events/1` (опубликовано) | 200 |

- Нужна зависимость «пользователь, если вошёл, иначе `None»` — по образцу `CurrentUser`, но
  без 401. Назовите её `OptionalUser`.
- После исправления http://localhost:3000/events/4 показывает страницу 404, и `curl` получает
  код 404.

В `docs/hw-06.md` ответьте:
- почему 404, а не 403? Что узнал бы посторонний из ответа 403?
- войдите как Ирина через Swagger (http://localhost:8000/docs) и в том же браузере откройте
  http://localhost:3000/events/4. Что видно и почему? Подсказки: привязаны ли cookie к порту;
  кто запрашивает API, когда страницу собирает сервер Nuxt, и что он делает с cookie браузера.
  Проверьте ответ в окне инкогнито.

## Часть 2. Страница клуба (3 балла)

Адрес `/clubs/<slug>`, например http://localhost:3000/clubs/chess.

API:
- в ответ клуба (`schemas.Club`) добавьте `slug` и `description` — проверьте, что афиша и
  справочник клубов не сломались;
- `GET /api/clubs/slug/{slug}` — клуб по slug; 404, если такого нет.

Страница:
- название и описание клуба, ниже — его опубликованные мероприятия карточками `EventCard`;
- если мероприятий нет — «У клуба пока нет мероприятий»;
- метатеги: `title`, `description`, `og:title`, `og:description`, `og:image` (полный адрес),
  `og:url`;
- несуществующий slug (`/clubs/nope`) — страница 404 и код 404;
- в карточке мероприятия название клуба становится ссылкой на страницу клуба.

## Часть 3. «Ближайшие 7 дней» (2 балла)

На афише рядом с фильтром по клубам — переключатель «Все даты / Ближайшие 7 дней».

- Состояние — в адресе: `/?days=7`, вместе с клубом — `/?club=1&days=7`.
- Используйте параметры `date_from` и `date_to` API, они уже есть: `date_from` — сегодня,
  `date_to` — сегодня плюс 7 дней (API включает обе даты).
- «Сегодня» — по Томску, а не по часовому поясу сервера или браузера. Подсказка:
  `new Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Tomsk' }).format(date)` даёт
  `2026-10-16`.
- На демо-данных: с `?days=7` — 3 мероприятия (резюме, Яндекс, шахматный турнир).
- Переключение по клику — без перезагрузки страницы; `curl 'localhost:3000/?days=7'` отдаёт уже
  отфильтрованный HTML.

## Часть 4. Измерить разницу (2 балла)

DevTools → Lighthouse, режим Mobile, категории Performance и SEO. Замерьте главную страницу
дважды:
1. как есть;
2. с временным правилом `'/': { ssr: false }` в `routeRules` (после замера — убрать).

В `docs/hw-06.md` — таблица: First Contentful Paint, Largest Contentful Paint, Total Blocking
Time, оценка SEO — для обоих вариантов. И ответы:
- какой показатель изменился сильнее всего и почему;
- что видит робот мессенджера в каждом из вариантов (приложите вывод
  `curl -s localhost:3000 | grep -c 'class="card"'`).

Замеры в режиме разработки хуже, чем будут на рабочем сервере: код не сжат, модули грузятся
по одному. Сравнивайте варианты между собой, а не с «нормами».
