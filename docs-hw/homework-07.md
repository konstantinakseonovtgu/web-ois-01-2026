# Задание к практике 7

## Часть 1. Регистрация на сайте (3 балла)

Страница `/register`: имя, email, пароль. Ссылка на неё — со страницы входа.

- BFF `POST /bff/register`: создаёт пользователя (`POST /api/auth/register`) и **сразу входит**
  под ним (`POST /api/auth/login`), чтобы человеку не вводить пароль второй раз. Браузер делает
  один запрос и получает cookie сессии.
- После регистрации — в шапке имя нового пользователя, переход на `next` (как у входа).
- Ошибки — по-русски и рядом с полем, к которому относятся:

| Ситуация | Ответ API | Что видит человек |
|---|---|---|
| email уже занят | 409 | «Этот email уже зарегистрирован» под полем email |
| пароль короче 15 символов | 422, `loc` оканчивается на `password` | «Пароль — не короче 15 символов» под полем пароля |
| email не похож на email | 422, `loc` оканчивается на `email` | «Проверьте адрес почты» |

- Минимальная длина пароля подсказана и браузеру (`minlength`), но работает и без неё —
  проверьте, удалив атрибут в DevTools.

В `docs/hw-07.md`: почему вход после регистрации сделан в BFF, а не вторым запросом из браузера?
Что будет, если регистрация прошла, а вход — нет (например, API перезапустился между запросами)?
Как ваш код это обрабатывает?

## Часть 2. Изменение мероприятия (3 балла)

Страница `/events/<id>/edit` — та же форма, что у создания, заполненная текущими значениями.

- Вынесите форму в компонент `EventForm.vue`; `new.vue` и `edit.vue` используют его.
- BFF `PATCH /bff/events/:id` → `PATCH /api/events/{id}`; номер — только цифры, как в `idParam`.
- Кнопка «Изменить» на странице мероприятия — только тем, кто может им управлять: администратору
  и организаторам клуба. Остальные кнопку не видят, а прямой заход на `/edit` даёт 403.
- Время в форме — по Томску, как при создании: `starts_at` из API нужно разложить на дату и
  время именно томские, а не в часовом поясе браузера.
- После сохранения — страница мероприятия с новыми данными. Ошибки BR-1, BR-6, BR-7 — в форме.

Проверка: Глеб (`chess@`) не видит кнопку у мероприятий IT-клуба, а `PATCH` в обход интерфейса
(curl с его cookie) получает 403 от API.

## Часть 3. Список участников (2 балла)

На странице мероприятия для организаторов клуба и администратора — блок «Участники (N)»: имя и
время записи, по порядку записи.

- BFF `GET /bff/events/:id/participants` → `GET /api/events/{id}/registrations` (BR-10).
- В HTML страницы от сервера списка нет: он запрашивается в браузере, как статус записи в
  `RegisterButton`. Проверьте `curl` страницы под cookie организатора — фамилий в нём нет.
- Email участников BFF **не передаёт** в браузер: на странице он не нужен.

В `docs/hw-07.md`: почему список участников нельзя вписывать в HTML страницы с сервера, если
страницу когда-нибудь будут кешировать? Почему убрать email в BFF лучше, чем просто не
показывать его в шаблоне?

## Часть 4. Кеш и личное (2 балла)

Представьте, что для разгрузки сервера на главную включили кеш:

```ts
routeRules: {
  '/': { swr: 60 },
}
```

В `docs/hw-07.md` ответьте:
1. Анна вошла и открыла `/`. Через 10 секунд гость открыл `/`. Что гость увидит в шапке и
   почему? Пройдите по коду: где узнаётся пользователь, где это значение попадает в HTML и в
   данные страницы.
2. Опасно ли это для данных, то есть может ли гость после этого что-то сделать от имени Анны?
   Обоснуйте через то, что проверяет API.
3. Предложите два способа совместить кеш главной и шапку с именем. Для каждого — чем
   заплатим.

По желанию (+1 балл сверх десяти): включите правило, повторите сценарий в двух окнах и опишите,
совпало ли увиденное с предсказанием. Если в режиме разработки кеш вёл себя не так, как вы
ожидали, — так и напишите, это тоже результат.

## Критерии оценки

| Критерий | Баллы |
|---|---|
| Регистрация: один запрос из браузера, сразу вход, ошибки у полей, ответы в `hw-07.md` | 3 |
| Изменение: общий компонент формы, кнопка только своим, 403 при прямом заходе, время по Томску | 3 |
| Участники: только своим, не в HTML от сервера, без email | 2 |
| Кеш и личное: точный разбор сценария и два способа с ценой | 2 |
