# Задание к практике 5

## Часть 1. Мои записи и отмена (3 балла)

Теперь, когда известно, кто делает запрос, перенесите отмену записи из задания 4 на правильный
адрес и добавьте список своих записей.

| Эндпоинт | Что делает | Коды |
|---|---|---|
| `DELETE /api/events/{event_id}/registrations/me` | BR-5: отменяет запись текущего пользователя, `status = 'cancelled'` | 204; 401; 404 — активной записи нет; 409 — мероприятие началось |
| `GET /api/me/registrations` | активные записи текущего пользователя: id мероприятия, название, начало, аудитория — по возрастанию времени | 200; 401 |

Список строится **одним-двумя** запросами к базе независимо от числа записей (проверьте с
`SQL_ECHO: "1"`).

## Часть 2. Смена пароля (2 балла)

`POST /api/auth/password` с телом `{"old_password": "...", "new_password": "..."}`:

- 401 — не выполнен вход; 400 — старый пароль неверен; 422 — новый короче 15 символов;
- новый пароль сохраняется хешем Argon2;
- после смены **все остальные** сессии пользователя удаляются, текущая продолжает работать.

В `docs/hw-05.md` объясните, зачем удалять остальные сессии, и проверьте: войдите под одним
пользователем в двух окнах, смените пароль в первом — второе должно получить 401.

## Часть 3. Ограничение попыток входа (2 балла)

Сейчас пароль можно перебирать сколько угодно. Добавьте ограничение: не больше 5 неудачных
попыток входа для одного email за 15 минут. Шестая попытка — `429 Too Many Requests` с текстом
«Слишком много попыток, попробуйте через N минут», **даже если пароль верный**.

- Попытки храните в базе (новая таблица через миграцию), а не в памяти процесса.
- Успешный вход неудачные попытки не обнуляет задним числом — считаются попытки за последние
  15 минут.

В `docs/hw-05.md` ответьте: почему при шестой попытке нельзя отвечать «пароль верный, но
подождите»? Почему счётчик в памяти процесса не годится, если API запущен в нескольких копиях?

## Часть 4. Журнал действий в базе (3 балла)

Сейчас журнал админки пишется только в лог — он пропадёт при перезапуске и в нём неудобно искать.

- Таблица `audit_log` через миграцию: время, `user_id` администратора, действие, раздел
  (`identity`), id объекта, изменения в `jsonb`.
- Свой класс-наследник `AuditBackend` из `sqladmin.audit`, который пишет туда. Подключите его
  вместо `LoggingAuditBackend`. Действия «Опубликовать» и «Отклонить» тоже попадают в журнал.
- Раздел «Журнал» в админке только для чтения: без создания, правки и удаления; сортировка
  по времени, новые сверху.
- «Отклонить» без заполненной причины (`reject_reason`) не срабатывает: мероприятие остаётся на
  модерации, администратор видит сообщение об ошибке (`Flash.error`).

## Критерии оценки

| Критерий | Баллы |
|---|---|
| Отмена записи и «мои записи»: коды, статус вместо удаления, без N+1 | 3 |
| Смена пароля: проверки, хеш, остальные сессии удалены; ответ в `hw-05.md` | 2 |
| Ограничение попыток: таблица, 429, ответы на вопросы | 2 |
| Журнал в базе, раздел только для чтения, отклонение только с причиной | 3 |
